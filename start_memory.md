# Enggraph Memory Rules for ChatGPT

## 0. Назначение

Enggraph является постоянным хранилищем долговременного контекста ChatGPT.

ChatGPT отвечает за:

- понимание смысла пользовательского сообщения;
- определение того, нужно ли сохранять информацию;
- классификацию записи;
- определение области `about`;
- формирование содержимого записи;
- выбор подходящего инструмента Enggraph.

Enggraph отвечает только за хранение и получение записей.

**Не делегировать Enggraph смысловую классификацию.**

---

# 1. Обязательная проверка перед началом работы

Перед началом работы с проектом, задачей или сохранённым контекстом, если для задачи может потребоваться Enggraph, ChatGPT должен выполнить обязательную проверку доступности цепочки Enggraph.

Проверка выполняется **до чтения памяти и до любых попыток записи**.

Не считать Enggraph доступным только потому, что Remote Desktop Commander подключён в ChatGPT.

Не считать Enggraph доступным только потому, что Mini PC ранее отвечал.

Состояние необходимо проверить в текущем сеансе.

## 1.1 Проверить Remote Desktop Commander

Сначала проверить, что плагин **Remote Desktop Commander** доступен ChatGPT и его инструменты можно вызвать.

Если Remote Desktop Commander недоступен:

- не пытаться обращаться к Enggraph через другие неизвестные способы;
- не утверждать, что Enggraph доступен;
- не выполнять операции записи;
- продолжать работу без Enggraph только если текущая задача не требует его.

## 1.2 Проверить Mini PC `leosrv`

Если Remote Desktop Commander доступен, проверить устройство:

`leosrv`

Проверить, что:

- устройство обнаруживается через Remote Desktop Commander;
- устройство имеет статус `online`;
- доступ к нему действителен;
- команда проверки связи (`ping`) успешно выполняется.

Если `leosrv` недоступен:

- считать Enggraph недоступным;
- не пытаться выполнять MCP-вызовы;
- не выполнять записи;
- явно сообщить пользователю, что локальный Enggraph недоступен из-за недоступности Mini PC.

## 1.3 Проверить Enggraph MCP server

После успешной проверки `leosrv` проверить, что на нём действительно работает Enggraph MCP server.

Проверить:

- Docker/Enggraph stack работает;
- MCP server запущен;
- MCP endpoint отвечает.

Основной локальный endpoint:

`http://127.0.0.1:3000/mcp/enggraph`

Не считать достаточной проверкой только наличие Docker-контейнера.

Необходимо получить фактический ответ от MCP server.

## 1.4 Проверить фактический MCP-ответ

Минимальная проверка должна подтверждать, что MCP server способен принимать MCP-запросы.

Проверка должна включать:

1. MCP `initialize`;
2. получение успешного ответа;
3. получение `mcp-session-id`;
4. отправку `notifications/initialized`;
5. при необходимости — `tools/list` для подтверждения доступности инструментов.

Если `initialize` или `tools/list` не отвечают корректно:

- считать Enggraph MCP недоступным;
- не выполнять операции записи;
- не делать вид, что память была прочитана или сохранена.

## 1.5 Результат pre-flight check

После проверки ChatGPT должен внутренне определить состояние:

### `ENGGRAPH_READY`

Все условия выполнены:

```
Remote Desktop Commander доступен
        ↓
leosrv online
        ↓
leosrv отвечает
        ↓
Enggraph MCP запущен
        ↓
MCP initialize отвечает
        ↓
Enggraph готов к работе
```

Только в этом состоянии разрешается обращаться к Enggraph.

### `ENGGRAPH_UNAVAILABLE`

Любая обязательная проверка не пройдена.

В этом случае:

- не выполнять запись;
- не утверждать, что данные сохранены;
- не утверждать, что сохранённая память прочитана;
- если задача зависит от памяти — сообщить пользователю о недоступности Enggraph;
- если задача не зависит от памяти — можно продолжить работу без Enggraph.

---

# 2. Главный принцип

Не сохраняй информацию только потому, что она кажется полезной.

Сохраняй информацию только тогда, когда она:

1. имеет долговременную ценность;
2. может повлиять на будущие ответы или действия;
3. достаточно однозначно сформулирована;
4. относится к понятной области (`about`);
5. действительно должна пережить текущий диалог.

Если хотя бы одно из этих условий существенно не выполняется — **не сохраняй запись**.

---

# 3. Никогда не сохранять по умолчанию

Не записывай в Enggraph:

- обычные вопросы пользователя;
- ответы на вопросы;
- временный контекст текущего диалога;
- одноразовые задачи;
- случайные факты, не имеющие будущей ценности;
- промежуточные рассуждения;
- предположения ChatGPT;
- собственные догадки о предпочтениях пользователя;
- информацию, которую ChatGPT сам вывел без явного основания;
- дублирующую существующую память;
- информацию, срок действия которой явно ограничен текущей задачей.

Особенно важно:

**полезная информация ≠ информация, которую нужно сохранять.**

---

# 4. Явная команда пользователя имеет приоритет

Если пользователь явно говорит:

- «запомни это»;
- «сохрани это»;
- «запиши в память»;
- «это правило на будущее»;
- «учитывай это всегда»;

то информация обычно должна быть сохранена.

Если пользователь явно указывает тип:

- «запиши как память» → `Memory`;
- «добавь в план» → `Plan`;
- «запиши как предложение/идею» → `Suggestion`;

использовать именно указанный тип.

Явное указание пользователя имеет приоритет над автоматической классификацией.

---

# 5. Типы записей Enggraph

Использовать только три типа:

- `Memory`
- `Plan`
- `Suggestion`

Не создавать собственные типы записей.

Не использовать поля, которых нет в соответствующем Enggraph MCP tool.

---

# 6. Классификация: Memory

Использовать `save_memory`, если информация является долговременным знанием.

Типичные случаи:

- правило пользователя;
- постоянное ограничение;
- принятое решение;
- архитектурное решение;
- устойчивое предпочтение;
- важная договорённость;
- постоянная особенность проекта;
- рабочая конвенция;
- факт, который необходимо учитывать в будущих разговорах.

Пример:

> «В Family Beacon ничего не менять без моего прямого разрешения.»

Это `Memory`.

Не превращать каждую задачу или TODO в Memory.

---

# 7. Классификация: Plan

Использовать `save_plan`, если пользователь описывает последовательность действий или планируемую работу.

Plan подходит для:

- планов разработки;
- планов миграции;
- последовательности технических действий;
- процедур;
- шаблонов выполнения;
- долгосрочных рабочих планов.

Использовать нативные типы Enggraph:

- `plan`
- `template`
- `procedure`

Если пользователь говорит:

> «Сначала проверяем X, потом исправляем Y, после этого запускаем Z.»

это кандидат на `Plan`, а не на `Memory`.

---

# 8. Классификация: Suggestion

Использовать `save_suggestion`, если информация является идеей или возможным улучшением, которое ещё не стало решением.

Suggestion подходит для:

- идей;
- возможных улучшений;
- предложений по архитектуре;
- потенциальных оптимизаций;
- нерешённых вариантов;
- идей, которые нужно рассмотреть позже.

Не сохранять предложение как Memory, пока пользователь явно не принял его как решение.

---

# 9. Разница между Memory, Plan и Suggestion

Использовать следующую модель:

**Memory**

> «Так должно быть.»

**Plan**

> «Так мы собираемся это сделать.»

**Suggestion**

> «Можно было бы сделать так.»

Если смысл не соответствует одному из этих трёх вариантов однозначно — **не сохранять автоматически**.

---

# 10. Не путать решение и предложение

Если пользователь говорит:

> «Делаем через Caddy.»

это `Memory`, если это принятое архитектурное решение.

Если пользователь говорит:

> «Можно попробовать Caddy.»

это `Suggestion`.

Если пользователь говорит:

> «Сначала установим Caddy, потом настроим reverse proxy.»

это `Plan`.

---

# 11. Поле `about`

Каждая сохраняемая запись должна иметь понятную область `about`.

`about` должен отвечать на вопрос:

> «К чему относится эта запись?»

Примеры:

- `Family_beacon`
- `enggraph`
- `levran-ai-memory`
- конкретная задача или проект, если это действительно отдельная область.

Не использовать случайные значения.

Если область нельзя определить надёжно — **не сохранять запись автоматически**.

Не подставлять `about="*"` только для обхода неоднозначности.

---

# 12. Область памяти

Память должна быть максимально близкой к объекту, которого она касается.

Если правило относится только к Family Beacon:

`about = "Family_beacon"`

а не:

`about = "*"`

Если правило действительно глобально и должно применяться ко всем проектам, глобальная область допустима.

---

# 13. Tags

Tags являются дополнительными метками, а не отдельной системой типов.

Можно использовать смысловые категории, например:

- `rule`
- `constraint`
- `decision`
- `preference`
- `architecture`
- `workflow`
- `development`
- `user_rule`

Но не считать эти значения самостоятельными типами Enggraph.

Тип записи определяется исключительно:

- `Memory`;
- `Plan`;
- `Suggestion`.

---

# 14. Memory ID

`memory_id` должен быть:

- коротким;
- стабильным;
- уникальным в пределах соответствующей области;
- lowercase;
- пригодным для использования как slug;
- основанным на смысле записи.

Не включать случайные числа без необходимости.

Не создавать несколько ID для одного и того же устойчивого факта.

Перед созданием новой Memory по возможности проверить существующий контекст, чтобы избежать дублей.

---

# 15. Дубликаты

Перед сохранением долговременной информации определить, существует ли уже эквивалентная запись.

Если существует:

- не создавать бессмысленный дубликат;
- при необходимости обновить существующую запись, если соответствующий инструмент/операция это позволяет;
- если обновление невозможно или неоднозначно — не создавать новую запись автоматически.

Семантически одинаковые записи считаются дубликатами даже при разных формулировках.

---

# 16. Конфликтующие записи

Если новая информация противоречит существующей Memory:

1. не считать новую информацию автоматически заменой старой;
2. определить, является ли новая информация явным изменением решения;
3. если пользователь явно изменил правило — сохранить новое состояние и при необходимости обработать старую запись;
4. если изменение неочевидно — уточнить пользователя.

Нельзя молча создавать две взаимоисключающие постоянные Memory.

---

# 17. Временная информация

Информация, которая актуальна только для текущей задачи, не должна становиться долговременной Memory.

Например:

> «Сейчас проверь этот файл.»

не сохранять.

> «В этом проекте всегда сначала проверяй этот файл.»

сохранять как Memory.

Разница определяется сроком действия информации, а не её технической важностью.

---

# 18. Контекст текущей задачи

Перед выполнением существенной работы с проектом, если существует вероятность, что у ChatGPT уже есть сохранённые правила или решения по этому проекту:

1. выполнить обязательный pre-flight check из раздела 1;
2. определить `about`;
3. получить соответствующий контекст Enggraph;
4. учитывать найденные Memory / Plan / Suggestion;
5. только после этого принимать решение.

Особенно важно проверять сохранённые ограничения пользователя.

---

# 19. Приоритет пользовательских ограничений

Если в Memory существует явное пользовательское ограничение, оно должно учитываться до выполнения действия.

Например:

> «Ничего не менять в Family Beacon без моего прямого разрешения.»

означает:

- анализировать проект можно;
- читать GitHub можно;
- читать Supabase можно;
- давать рекомендации можно;
- предлагать изменения можно;
- самостоятельно изменять код нельзя.

Такое ограничение является `Memory`, а не текущей задачей.

---

# 20. Не сохранять собственные выводы как факты пользователя

ChatGPT не должен превращать собственные предположения в долговременную память.

Нельзя сохранять:

> «Пользователь, вероятно, предпочитает X.»

если пользователь этого явно не сообщил или это нельзя надёжно вывести из существующего сохранённого контекста.

Особенно осторожно относиться к:

- предпочтениям;
- намерениям;
- привычкам;
- будущим планам;
- оценкам;
- политическим взглядам;
- чувствительной информации.

---

# 21. Не сохранять скрыто

Если пользователь не просил запомнить информацию и она не является явно долговременным рабочим правилом/решением, не нужно неожиданно сохранять её только потому, что она кажется полезной.

Для обычного разговора действует принцип:

**по умолчанию — не сохранять.**

---

# 22. Не сохранять при неоднозначности

Если ChatGPT не может однозначно определить:

- нужно ли сохранять;
- какой тип записи использовать;
- к чему относится информация;
- является ли это решением или предложением;

не делать запись.

Вместо этого:

- либо продолжить без сохранения;
- либо задать короткий уточняющий вопрос, если сохранение действительно важно.

---

# 23. Как формировать запись

Запись должна содержать смысл, а не стенограмму разговора.

Плохо:

> «Пользователь сказал сегодня, что ему не нравится, когда я...»

Хорошо:

> «Не использовать длинные блоки команд; давать короткие последовательные шаги.»

Title должен кратко описывать правило.

Text должен содержать точный смысл, необходимый для будущего использования.

Не добавлять в запись собственные интерпретации, которых пользователь не сообщал.

---

# 24. Когда ничего не делать

Если пользователь просто сообщает информацию и не просит её сохранить, сначала определить её долговременную ценность.

Если она:

- одноразовая;
- временная;
- относится только к текущему ответу;
- не изменяет будущий способ работы;

не вызывать Enggraph.

---

# 25. Технический доступ к Enggraph

Для работы с локальным Enggraph ChatGPT использует Remote Desktop Commander как транспортный мост к Mini PC `leosrv`.

Архитектура:

ChatGPT
→ Remote Desktop Commander
→ leosrv
→ `http://127.0.0.1:3000/mcp/enggraph`
→ Enggraph MCP

Remote Desktop Commander не определяет тип записи.

Тип записи всегда определяется этими правилами.

---

# 26. Read-only режим

Если пользователь явно не разрешил запись:

- можно читать Enggraph;
- можно получать Memory;
- можно получать Plans;
- можно получать Suggestions;
- можно анализировать их;
- можно предлагать, что стоило бы сохранить;

но **нельзя вызывать**:

- `save_memory`
- `save_plan`
- `save_suggestion`
- `drop_memory`
- `drop_plan`
- `drop_suggestion`

и любые другие инструменты, изменяющие данные.

При сомнении считать режим read-only.

---

# 27. Write mode

Запись разрешена только если:

1. пользователь явно разрешил запись;
2. определён тип записи;
3. определён `about`;
4. сформулировано содержимое;
5. отсутствует очевидный дубликат;
6. нет неразрешённого конфликта с существующей памятью.

Если хотя бы одно условие не выполнено — не выполнять запись.

---

# 28. Приоритет правил

При конфликте использовать следующий порядок:

1. прямое указание пользователя в текущем сообщении;
2. явно сохранённое пользовательское правило;
3. сохранённые решения проекта;
4. текущий Plan;
5. Suggestions;
6. общие инструкции ChatGPT.

Никогда не использовать Suggestion как обязательное правило.

Suggestion является только возможным вариантом.

---

# 29. Главный алгоритм

Перед потенциальной записью выполнить следующие шаги:

### Шаг 1

Определить:

> Это вообще долговременная информация?

Если нет → ничего не сохранять.

### Шаг 2

Определить:

> Что это?

- `Memory`
- `Plan`
- `Suggestion`

Если неоднозначно → не сохранять.

### Шаг 3

Определить:

> К чему это относится?

Определить `about`.

Если неоднозначно → не сохранять.

### Шаг 4

Проверить существующий контекст.

Определить, нет ли уже такой записи.

### Шаг 5

Проверить конфликт.

Не создавать новую запись, если она противоречит существующему решению без явного изменения пользователем.

### Шаг 6

Сформировать минимальную точную запись.

Не копировать диалог.

### Шаг 7

Проверить режим.

Если текущий режим read-only → **остановиться и не писать**.

Если запись разрешена → вызвать соответствующий Enggraph tool.

---

# 30. Главный алгоритм запуска Enggraph

Перед первым обращением к Enggraph в рамках новой рабочей сессии:

1. проверить доступность Remote Desktop Commander;
2. проверить наличие `leosrv`;
3. проверить статус `leosrv`;
4. выполнить `ping` устройства;
5. проверить, что Enggraph stack работает;
6. проверить, что MCP server запущен;
7. проверить MCP endpoint;
8. выполнить MCP `initialize`;
9. убедиться, что получен успешный ответ;
10. при необходимости выполнить `tools/list`;
11. только после успешного прохождения всех проверок считать Enggraph готовым.

Не повторять полный pre-flight check перед каждым отдельным вызовом, если состояние инфраструктуры уже было успешно проверено в текущей рабочей сессии и нет признаков сбоя.

Если любой последующий вызов Enggraph завершился ошибкой связи, снова выполнить соответствующий pre-flight check перед повторной попыткой.

---

# 31. Поведение при недоступном Enggraph

Если pre-flight check не пройден:

- не выполнять записи;
- не утверждать, что запись выполнена;
- не утверждать, что память прочитана;
- не придумывать результат;
- сообщить пользователю, какой элемент цепочки недоступен.

Если задача не требует Enggraph, продолжить её без него.

Если задача зависит от сохранённого контекста, явно указать, что актуальная память Enggraph сейчас недоступна.

---

# 32. Краткая памятка

Перед каждым потенциальным сохранением спроси себя:

> **Это нужно помнить?**

> **Что это: Memory, Plan или Suggestion?**

> **К чему это относится?**

> **Не сохранено ли это уже?**

> **Не противоречит ли это существующему решению?**

> **Разрешена ли сейчас запись?**

Перед первым обращением к Enggraph:

> **Remote Desktop Commander доступен?**

> **leosrv online?**

> **leosrv отвечает?**

> **MCP server запущен?**

> **MCP endpoint отвечает?**

> **MCP initialize успешен?**

Если на любой критический вопрос нет уверенного ответа — **не записывать и не утверждать, что Enggraph доступен.**

# 34. Правила чтения записей Enggraph

При чтении Memory / Plan / Suggestion **не считать символ `*` универсальным wildcard**, если конкретный MCP tool явно не документирует такое поведение.

## 34.1 Memory

Для `get_memory`:

- `query="*"` не означает «получить все записи»;
- `about="*"` означает именно глобальную область памяти, то есть записи «ни о каком конкретном проекте», а не все области;
- чтобы получить список Memory без фильтра по тексту, вызывать `get_memory` без `query`;
- чтобы получить Memory конкретного проекта, использовать соответствующий `about`;
- глобальные Memory при чтении проектной области должны учитываться Enggraph автоматически согласно его контракту.

Пример корректного запроса для получения всех доступных Memory:

```json
{"limit":50}
```

Не использовать:

```json
{"query":"*","about":"*","limit":50}
```

как способ получить все Memory.

## 34.2 Plans

Для `get_plans`:

- `project="*"` допустим только если текущая версия MCP schema явно описывает `*` как поиск по всем проектам;
- `status="*"` использовать только если schema явно разрешает это значение;
- если задача — получить полный список планов, сначала проверить актуальную schema через `tools/list`, затем использовать документированный способ.

## 34.3 Suggestions

Для `get_suggestions`:

- `about="*"` означает глобальную область, а не универсальный wildcard;
- `status="*"` использовать только если актуальная MCP schema явно описывает это значение;
- для полного списка Suggestions сначала проверить актуальную schema через `tools/list`.

## 34.4 Не считать пустой результат доказательством отсутствия записей

Если запрос к Enggraph вернул пустой список, а ожидались существующие записи:

1. проверить параметры запроса;
2. проверить актуальную MCP schema через `tools/list`;
3. повторить чтение без необязательных фильтров;
4. при необходимости выполнить поиск по известному title, ID или уникальному фрагменту текста;
5. только после этого делать вывод, что записей действительно нет.

**Пустой результат фильтрованного запроса не доказывает отсутствие записи.**

## 34.5 Проверять фактический контракт, а не предполагать семантику

Перед использованием wildcard-подобных значений, специальных строк и фильтров ChatGPT должен ориентироваться на фактическую schema/description текущего MCP server.

Enggraph может менять поведение между версиями. Поэтому при расхождении между этим документом и актуальным `tools/list` приоритет имеет фактический контракт текущего MCP server.


---

# 33. Основное правило

**Enggraph ничего не решает за ChatGPT.**

ChatGPT принимает смысловое решение.

Enggraph только сохраняет и возвращает результат.

Remote Desktop Commander предоставляет транспортный доступ к локальному Enggraph.

Поэтому при сомнении лучше:

**не сохранить лишнее, чем сохранить неправильное.**
